Every page of a Mateu app belongs to one of **six page types**. The type is a business decision
(*what is the user doing on this screen?*), not a layout decision, and it is the first thing to
settle for each screen. The names follow the families of the Oracle Redwood page templates, the
clearest public taxonomy for business UIs, and every page carries its type on the wire as
`pageType`.

| Type | The user is… | Typical templates | Default width |
|---|---|---|---|
| [**Collection**](#collection) | finding things in a set: searching, listing, opening, editing | CRUD, smart search, to-do list, calendar, collection detail, data management | from the content |
| [**Detail**](#detail) | looking at *one* thing in depth | item overview, general overview, foldout, Gantt page | from the content |
| [**Form**](#form) | completing one task: some fields, one action | create & edit, advanced create & edit, task-centric page | fixed |
| [**Process**](#process) | moving through steps toward a result | wizard (bar, steps, rail), guided import | fixed |
| [**Dashboard**](#dashboard) | monitoring numbers to decide what needs attention | dashboard | from the content |
| [**Landing**](#landing) | arriving: orientation and ways in | welcome, hero search | fixed |

To pick a type, ask at most three questions, in order:

1. **Many records or one?** Many → *collection*. One → *detail*.
2. **Is the user changing something?** In one shot → *form*. Across steps → *process*.
3. **Neither?** Watching numbers → *dashboard*. It's the front door → *landing*.

Then pick the template within the type with the decision guide,
[Choosing a page template](/ux-patterns/choosing-a-page-template/), and see every template with its
demo route in [Page templates](/ux-patterns/page-templates/).

## How a page gets its type

A page's type is resolved in this order:

1. **Declared.** In Java `@PageTemplate(PageType.DASHBOARD)`, in C#
   `[PageTemplate(PageType.Dashboard)]`, in Python `@page_template(PageType.DASHBOARD)`. In YAML,
   a definition declares it with the `pageType:` key (for example `pageType: dashboard`), using
   the same six names as the wire.
2. **From the archetype.** Each archetype belongs to one type (the tables below say which).
3. **From the shape.** A `Listing` or CRUD is a collection; a view with `MetricCard` fields is a
   dashboard; a view made only of `Button` and component fields that `@AutoPage` composes as a
   welcome page is a landing; anything else is a form.

Inference goes one step further for the two shapes Mateu can derive entirely: with
[`@AutoPage`](/ux-patterns/layout-inference/#page-level-inference-autopage), a class of
`MetricCard` fields is *composed* as a dashboard, and a class of `Button` fields and panels as a
welcome page. For other shapes Mateu only advises: a plain form that looks like a known template
(a selectable list next to a detail pane, for instance) logs a one-time hint naming the archetype.
Below the type, [`@AutoLayout`](/ux-patterns/layout-inference/) infers sections, tabs and widgets.

What the type changes:

- the page's **default width** (below);
- the `data-page-type` attribute on the rendered page, a hook for stylesheets;
- a shared vocabulary for docs, conformance tests and the IDE page templates.

## Page width

Width is the first parameter of every page template:

| Width | What it does | Good for |
|---|---|---|
| **Fixed** | caps the content column at 1408 px and centres it | text and forms, which get harder to read when too wide |
| **Full width** | fluid, keeping 24 px side gutters | dense grids and tables |
| **Edge to edge** | no side margins | canvases: Gantt, planning board, foldout, map |

Resolution order: a declaration (`@PageWidth(FULL_WIDTH)`, C# `[PageWidth(PageWidthStyle.FullWidth)]`,
Python `@page_width(PageWidth.FULL_WIDTH)`, or the `PageWidthSupplier` hook) wins. Otherwise
**form, process and landing pages are fixed**, and collection, detail and dashboard pages are
inferred from their content: full-bleed canvases (Gantt, planning board, kanban, BPMN, map) → edge
to edge, a dense or inline-editable CRUD → full width, anything else → fixed. Three archetypes
declare theirs: `Foldout` and `GanttPage` are edge to edge, `DataManagement` is full width.

In YAML, the IDE's **New › Mateu › Page…** wizard writes the chosen width into the root layout's
`style` (see [IDE tooling](/native/ide-tooling/)).

## Collection

**For:** finding, comparing and acting on records in a set.

**Anatomy:** page header with the primary action (*New*), the smart search bar (free text + typed
filter chips + saved views), the results (table, list, cards, tree or master-detail), pagination,
and selection-driven bulk actions. A row opens the record, or edits it in a drawer.

**Components you meet here:** `Listing`, `GridColumn`, the filter bar, `Badge`/status columns,
`EmptyState`, `TaskQueue`, `Calendar`, `Kanban`.

| Template | Archetype or piece | Detail |
|---|---|---|
| Create & edit (CRUD) | `AutoCrud<T>` / `Crud<…>` | [Create and edit](/ux-patterns/create-and-edit/) |
| Listing with capabilities | `Listing<Row>` + `Searchable`, `Filterable`, `Navigable`, `Editable`, `Creatable`, `Deletable` | [Capability listings](/java-user-manual/build/capability-listings/) |
| Smart search page | `SmartSearchPage<Filters, Row>` | [Smart search](/ux-patterns/smart-search/) |
| To-do list | `TodoList<Row>` | [To-do list](/ux-patterns/to-do-list/) |
| Calendar | `CalendarPage` | [Calendar](/ux-patterns/calendar/) |
| Collection detail | `CollectionDetail<Row>` | [Collection detail](/ux-patterns/collection-detail/) |
| Data management (grid ⇄ Gantt) | `DataManagement` | [Data management](/ux-patterns/data-management/) |
| Split view, tree | `@SplitCrud`, `GridLayout.tree` | [Split view](/ux-patterns/split-view/), [Tree CRUD](/ux-patterns/tree-crud/) |

:::note[Imports]
The samples leave out their `import` lines and compile with single-type imports. Some names exist
in two Mateu packages (the `@Menu` annotation and the `Menu` record, `@Button` and `Button`…), so
wildcard imports of both packages fail with "reference is ambiguous" — see
[Java imports](/reference/java-imports/).
:::

Listing behaviours worth knowing: [filters and listing](/ux-patterns/filters-and-listing/),
[bulk actions](/ux-patterns/bulk-actions/), [saved views](/ux-patterns/saved-views/),
[totals and grouping](/ux-patterns/aggregates/), [column chooser](/ux-patterns/column-chooser/),
[inline editing](/ux-patterns/inline-crud-editing/), [guided import](/ux-patterns/guided-import/).

## Detail

**For:** understanding one record in depth, and moving to its peers.

**Anatomy:** a rich page header (title, status badges, KPIs, timestamp, peer navigation or a
record switcher), then the record's information grouped into panels: a sticky key-info panel and
tabs, property cards, lateral fold-out panels, or a canvas with a docked detail.

**Components you meet here:** `EntityHeader`, `Card` with property-list sections,
`TabLayout`, `FoldoutLayout`, `ContentLayout` (main + aside), `Timeline`, `Gantt`.

| Template | Archetype or piece | Detail |
|---|---|---|
| Item overview | `ItemOverview` | [Item overview](/ux-patterns/item-overview/) |
| General overview | `GeneralOverview<Row>` | [General overview](/ux-patterns/general-overview/) |
| Foldout | `Foldout` | [Foldout](/ux-patterns/foldout/) |
| Gantt page | `GanttPage` | [Gantt](/ux-patterns/gantt/) |
| Master-detail, editable view | `MasterDetailView`, `EditableView` / `AutoEditableView` | [Editable view](/java-user-manual/build/editable-view/), [master-detail](/java-user-manual/build/master-detail/) |
| Waterfall detail | composition: `EntityHeader` + full-width cards | [Waterfall detail](/ux-patterns/waterfall-detail/) |
| Detail without leaving the page | a read-only `Drawer` | [Drawer](/ux-patterns/drawer/) |

```yaml
# Key information on the left, the rest of the record in tabs on the right

  - type: Card
    style: "flex: 0 0 22rem; position: sticky; top: 0;"

        - {type: FormField, id: sku, label: SKU, dataType: string, readOnly: true, propertyRow: true}
        - {type: FormField, id: price, label: Price, dataType: money, readOnly: true, propertyRow: true}
  - type: TabLayout
    tabs:
      - {type: Tab, label: Details, active: true, content: {type: Text, text: Details go here}}
      - {type: Tab, label: History, content: {type: Text, text: History goes here}}
```

</TabItem>

## Form

**For:** completing one task: enter or change some fields and run one action.

**Anatomy:** page header (title, perhaps a timestamp and KPIs), the fields grouped into sections,
validation messages at the field, and the closing actions in the footer (*Cancel*, *Save*). Long
forms add a sticky section index (`@Toc`) or a contextual side panel (`@Aside`).

**Components you meet here:** `Form`, `FormLayout`, `FormField` with its
[stereotypes](/ux/components/#fields-and-field-types), `FormSection`, `Notice`, `Button`.

| Template | Archetype or piece | Detail |
|---|---|---|
| Create & edit | a plain `@UI` class, or the forms of an `AutoCrud` | [Create and edit](/ux-patterns/create-and-edit/) |
| Advanced create & edit | sections + `@Toc` or `@Aside`, header extras | [Advanced create & edit](/ux-patterns/advanced-create-and-edit/) |
| Task-centric page | one task, one primary action | [Task-centric page](/ux-patterns/task-centric/) |
| Partial forms | folded or optional groups | [Partial forms](/ux-patterns/partial-forms/) |

<Tabs syncKey="authoring">
<TabItem label="YAML">

```yaml
type: Form
title: New customer
content:
  - type: FormLayout
    content:
      - {type: FormField, id: name, label: Name, dataType: string, required: true}
      - {type: FormField, id: email, label: Email, dataType: string, stereotype: email}
      - {type: FormField, id: notes, label: Notes, dataType: string, stereotype: textarea, colspan: 2}
buttons:
  - {type: Button, label: Cancel, actionId: cancel, buttonStyle: secondary}
  - {type: Button, label: Save, actionId: save, buttonStyle: primary}
```

Bind it to a route with a view model that handles `save`, or give it an `actions:` entry with a
`restAction` for a page with no backend.

</TabItem>

```java
  @NotEmpty String subject;
  @Stereotype(FieldStereotype.textarea) String details;

  @Button

    return new Message("Thanks!");
  }
}
```

## Process

**For:** reaching a result through ordered steps: onboarding, check-in, an import, an end-of-day
run.

**Anatomy:** the step's form, a progress indicator (a bar, numbered steps, or a sticky side rail
with a `current | total` counter), *Back* / *Next*, the completion action on the last input step,
and a read-only result step.

**Components you meet here:** `ProgressBar`, `ProgressSteps`, `Form`, `Notice`, and for long
jobs the [long-running job](/ux-patterns/long-running-jobs/) progress.

| Template | Archetype or piece | Detail |
|---|---|---|
| Step-by-step / guided process | `Wizard` + `@WizardProgress(STEPS \| RAIL)` | [Wizard](/ux-patterns/wizard/) |
| Guided import | `ImportWizard<Row>` | [Guided import](/ux-patterns/guided-import/) |
| A process inside a drawer | `Drawer` + an embedded wizard | [Guided process drawer](/ux-patterns/drawer/) |

<Tabs syncKey="authoring">
<TabItem label="YAML">

```yaml
# One definition per step (signup/1, signup/2…), each routed; Next navigates to the next step
type: Form
title: Sign up
content:
  - {type: Text, text: "Step 1 of 3 — Your details", size: s}
  - {type: ProgressBar, value: 0.33}
  - type: FormLayout
    content:
      - {type: FormField, id: fullName, label: Full name, dataType: string, required: true}
      - {type: FormField, id: email, label: Email, dataType: string, stereotype: email, required: true}
buttons:
  - {type: Button, label: Next, actionId: next, buttonStyle: primary}
actions:
  - id: next
    steps:
      - {type: Navigate, route: signup/2}
```

</TabItem>
<TabItem label="Java">

```java
@UI("/onboarding")
@WizardProgress(WizardProgressStyle.STEPS)
public class Onboarding extends Wizard {

  AccountTypeStep accountType = new AccountTypeStep();   // each step: a class implementing WizardStep
  CompanyStep company = new CompanyStep();
  OnboardingResult result;                               // the last step: read-only result

  @WizardCompletionAction
  Object finish() {
    accounts.create(accountType, company);
    return null;
  }
}
```

The `Wizard` archetype handles navigation, progress, cross-step state and branching
(`stepApplies`).

</TabItem>
</Tabs>

## Dashboard

**For:** seeing at a glance what needs attention, and drilling in.

**Anatomy:** a band of KPI cards (each optionally clickable), then a responsive grid of titled
tiles (charts, short lists, notes). No form, no footer.

**Components you meet here:** `Scoreboard`, `MetricCard`, `ResponsiveGrid`, `DashboardPanel`,
`Chart`, `TrendChart`, `Stat`, `Meter`, `Funnel`, `Heatmap`.

| Template | Archetype or piece | Detail |
|---|---|---|
| Dashboard | `Dashboard`, or a class of `MetricCard` fields with `@AutoPage` | [Dashboard](/ux-patterns/dashboard/) |

<Tabs syncKey="authoring">
<TabItem label="YAML">

```yaml
type: VerticalLayout
content:
  - {type: Text, text: Sales, container: h2}
  - type: Scoreboard
    metrics:
      - {type: MetricCard, title: Revenue, value: "1.2M", unit: EUR, trend: up, trendLabel: +8% vs last month}
      - {type: MetricCard, title: Orders, value: "3,480", trend: up, trendLabel: +3%}
  - type: ResponsiveGrid
    columns: [{size: fill}, {size: fill}]
    content:
      - type: DashboardPanel
        title: Sales by region
        content:
          type: Chart
          chartType: bar
          chartData:
            labels: [May, Jun, Jul]
            datasets: [{label: North, data: [120, 135, 128]}, {label: South, data: [98, 104, 117]}]
      - type: DashboardPanel
        title: Latest orders
        content:
          type: Grid
          content:
            - {type: GridColumn, id: order, label: Order}
            - {type: GridColumn, id: total, label: Total, align: end}
          page:
            content:
              - {order: SO-1042, total: "1,250.00"}
              - {order: SO-1041, total: "860.50"}
```

</TabItem>
<TabItem label="Java">

```java
@UI("/dashboard")
@Title("Sales dashboard")
public class SalesDashboard extends Dashboard {

  MetricCard revenue = MetricCard.builder()
      .title("Revenue").value("1.2").unit("M€")
      .trend(MetricTrend.up).trendLabel("+8% vs last month").build();

  @Panel(title = "Notes")
  Markdown notes = new Markdown("- Summer campaign starts **July 15th**", null, null);
}
```

Consecutive `MetricCard` fields form the KPI band; `@Panel` fields become tiles.

## Landing

**For:** the front door of an app or a workflow: orientation and a few ways in.

**Anatomy:** a hero (title, subtitle, optional image or tone) with calls to action, then highlight
tiles; or a hero hosting a search with results as cards.

**Components you meet here:** `HeroSection`, `Button`, `ResponsiveGrid`, `FeatureGrid`,
`CalloutCard`, `Listing` as cards.

| Template | Archetype or piece | Detail |
|---|---|---|
| Welcome | `Welcome`, or `@WelcomeBanner` on any page | [Welcome page](/ux-patterns/welcome-page/) |
| Hero search | `HeroSearch<Filters, Row>` | [Hero search](/ux-patterns/hero-search/) |

## When no template fits

The templates are a starting point, not a cage. Every archetype is a composition of ordinary
components, so the same pieces compose freely in a page of your own (`ContentLayout`,
`EntityHeader`, `HeroSection`, `TaskQueue`, `Card`…), and a page you compose still declares its
type with `@PageTemplate` or `pageType:`. When even composition is not enough, see
[Extending the UI](/ux/extending/).
