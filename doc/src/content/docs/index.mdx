## The problem

Most business applications end up as two applications:

```text
backend → API → frontend → duplicated model → duplicated validation
```

That means duplicated concepts, duplicated validation, glue code, and one more project to keep
alive.

## The Mateu approach

```text
model (YAML · visual editor · Java · C# · Python) → one wire model → browser · phone · desktop
```

You declare what a screen contains; Mateu derives the screen. The model is files in your
repository, reviewed and released like any other code — not a project in somebody's cloud.

## One model, three ways to write it

:::note[Imports]
The samples leave out their `import` lines and compile with single-type imports. Some names exist
in two Mateu packages (the `@Menu` annotation and the `Menu` record, `@Button` and `Button`…), so
wildcard imports of both packages fail with "reference is ambiguous" — see
[Java imports](/reference/java-imports/).
:::

The same product listing, written three ways. Each produces the same model, and every renderer
draws it the same way.

<Tabs syncKey="authoring">
<TabItem label="YAML (no code)">

```yaml
# specs/ui/products.yaml
type: Listing
title: Products
searchable: true
rowsSource:
  ref: products            # an endpoint named once in sources.yaml
columns:
  - {type: GridColumn, id: name, label: Name}
  - {type: GridColumn, id: price, label: Price}
  - {type: GridColumn, id: status, label: Status, dataType: status}
```

Write it by hand, or let the visual editor in IntelliJ or VS Code write it.

</TabItem>
<TabItem label="Java">

```java
@UI("/products")
@Title("Products")
public class Products extends AutoCrud<Product> {
  @Override
  public CrudStore<Product> store() {
    return ProductStore.INSTANCE;
  }
}
```

</TabItem>
<TabItem label="C#">

```csharp
[UI("products"), Title("Products")]
public class Products : Crud<Product>
{
    public override IEnumerable<Product> Fetch(string? search) => Store.Search(search);
    public override Product? Get(string id) => Store.Get(id);
    public override void Save(Product p) => Store.Save(p);
    public override void Delete(string id) => Store.Delete(id);
}
```

</TabItem>
<TabItem label="Python">

```python
@ui("products")
@title("Products")
class Products(Crud[Product]):
    def fetch(self, search): return store.search(search)
    def get(self, id): return store.get(id)
    def save(self, entity): store.save(entity)
    def delete(self, id): store.delete(id)
```

</TabItem>
</Tabs>

## What a Mateu UI is made of

Whichever way you write it, a Mateu UI is built from the same blocks: a **mount** at a base path,
an **app shell** and its **menu**, **routes**, **pages** (layouts of components, with optional
**partials**), **actions**, **data sources** and the **state** they fill, plus the cross-cutting
**field types**, **translations**, **environments**, **access** rules and **project settings**.
[What a Mateu UI is made of](/concepts/building-blocks/) shows them on one diagram, with a small
product catalogue as the running example.

What those blocks look like to the people using the app (the shell, the six page types, the
component catalogue and how to extend it) is the [UX guide](/ux/).
