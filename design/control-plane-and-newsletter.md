# Control plane for distributed UIs + an editable newsletter

Status: **design, queued after GA** (agreed with Miguel, 2026-10-10).
Both use cases come from Riu: (1) domain teams contributing their UIs to several consoles,
(2) one person who wants to edit a newsletter WYSIWYG. They share a platform (versioned store,
publication per environment, permissions, an online studio) but are different problems: (1) manages
**UI composition**, (2) edits **content**.

---

## 1. Console control plane

### 1.1 Model: curated, not self-declared

Teams do **not** declare where their UI goes. Platform registers remote UIs once and then places
their menus into any console. Two maintenance screens:

**Remote UI registry**
- name, owner team, description;
- base URL **per environment** (dev / pre / pro);
- default audience / permissions (optional);
- **menu discovery**: the control plane loads the registered app through the ordinary
  `/mateu/v3` contract and lists its menu tree, so placement picks from a list instead of typing
  routes; plus a health indicator (does it answer).

**Consoles**
- a console = an app shell (`AppShell`): title, variant, header actions, widgets;
- menu entries pointing at a registered UI: the whole UI, one of its menus, or a single option;
- section/group, order, label override, permissions per entry (`@EyesOnly` semantics: roles,
  groups, scopes, permissions);
- preview of the composed console.

Output: the console's app shell with remote menus — exactly today's federation (`RemoteMenu`,
remote mounts) but **generated by the control plane** instead of written by hand. At runtime each
console fetches its composed shell; every option is still served by its own domain backend, so
there is **no deployment coupling** (a domain changing URL = edit the registry, all consoles pick it
up without redeploy).

Later, optionally: a domain auto-registers in the registry on deploy (CI step). Placement into
consoles stays manual.

### 1.2 Storage: GitOps with hot overrides (Miguel's choice)

- **Git is the desired state.** Registry and consoles are YAML (`type: RemoteUi`, `type: Console`
  — or the existing `AppShell` + `RemoteMenu` vocabulary extended), reviewed by PR.
- **The UI can change values on the spot** — a hot override layer on top of git, for trying things.
- **GitOps always wins**: every reconcile resets to git; hot overrides are discarded.
- When a change is settled, it goes into the YAML via PR and merge.

Details that make this workable day to day:

1. **Reconcile on git change** (webhook / merge) and at boot — **not** on a timer, or a test override
   would vanish before it can be tried. Per-console **"pause sync"** switch for long test sessions,
   auto-expiring (e.g. 8h), visible to everyone.
2. **Drift is visible.** Every hot-overridden value is flagged "differs from git" with the git value
   next to it, so nobody is surprised when the next merge resets it. A console list column shows
   "N overrides".
3. **"Promote to git"** from the UI: turns the current overrides into the YAML diff and opens the PR
   (GitHub/GitLab API). After merge the reconcile applies it and the flags disappear because the
   values now match.
4. **Policy per environment**: dev/pre free overrides; pro overrides disabled or audited (who, what,
   when — same audit as `@Auditable`).

Override storage: a small DB table `(console|remoteUi, path, value, author, at, expiresAt?)` applied
as an overlay when the control plane serves a shell — the same overlay idea as `environments`
(`Environments.overlay`), one layer above it.

### 1.3 Pieces, mostly existing

| Need | Have | New |
|---|---|---|
| Remote menus / mounts | federation, `RemoteMenu`, `AppShell` | — |
| Per-environment URLs | `environments` | registry entries carry them |
| Permissions per entry | YAML access keys / `@EyesOnly` | — |
| Hot reload of a console | live reload (`DevSpecs`, `/mateu/dev/events`) | a production-safe variant: the shell re-fetched on reconcile |
| Reading specs from somewhere other than the jar | `DevSpecs.classLoader` hook | `SpecsSource` SPI: files \| git \| control-plane HTTP |
| Studio screens | Mateu itself | two CRUDs + preview, built **in Mateu** (dogfooding) |

### 1.4 Slices

1. `SpecsSource` SPI (files, git checkout, HTTP) + reconcile endpoint.
2. Registry + consoles as YAML kinds with schema, composed shell served by the control plane.
3. Control plane app (Mateu): the two maintenance screens, menu discovery, health, preview.
4. Hot overrides + drift flags + pause sync + "promote to git" PR.
5. Optional auto-registration from CI.

Open questions: one control plane per organisation or per environment; how consoles authenticate
to it; caching when the control plane is down (consoles must keep serving the last known shell).

## 2. Newsletter edited WYSIWYG — the same page builder, another catalogue

Revised 2026-10-10 (Miguel): the WYSIWYG editor already exists or is being built in Riu's
`frontend-public-reference` — `building-blocks/layout-builder`, a framework-independent Lit web
component `<layout-builder>` for dynamic pages built from **prebuilt components**:

- input `components: Catalog` (`{ id, nombre, imagen?, colspan? }`) and `layout: Layout` — a tree of
  `component` leaves (`componentId`, `colspan`, `parametros` key/value) and nestable `container`s, every
  container a 12-column grid;
- output event `layout-change` with the full `layout` tree + a flat `usages` projection;
- its integration into the control-plane's `DynamicPages` CRUD (a Mateu app) is still pending.

So the newsletter does **not** need GrapesJS or a second editor: it is the **same builder with an
email catalogue**. What differs is only the output:

| | Dynamic web page | Newsletter |
|---|---|---|
| Editor | `<layout-builder>` | `<layout-builder>` (same) |
| Catalogue | web components of the design system | email-safe components (header, text, image, button, columns, footer…) |
| Stored | layout tree (JSON) | layout tree (JSON) |
| Rendered by | data-plane (Astro + islands) | server-side to email HTML — one **MJML** template per catalogue component (MIT), tables + inline styles that survive Outlook/Gmail |
| Around it | DynamicPages CRUD | newsletter CRUD: draft/scheduled/sent, audiences, scheduling, sending, approval, history |

### What Mateu has to provide (the reusable part)

1. **A generic "web component field"**: bind ANY custom element to a form field — script URL + tag,
   inputs as properties (the value, plus extra properties such as the catalogue), output = a named
   event whose `detail` (or a path in it) becomes the field value. Mateu should not know about
   `layout-builder`; the control-plane declares it. This is exactly the missing piece for the pending
   `DynamicPages` integration, and every future building block (image picker, map editor…) reuses it.
   Check first what `CustomField` / `Element` / `MicroFrontend` already cover; add only what is
   missing (value binding + event mapping + passing non-string properties), across Vaadin and
   Redwood (Redwood hosts it as a plain custom element), with RN/IntelliJ showing a read-only
   summary.
2. **Preview**: an action that renders the stored layout (web: the data-plane URL in an iframe;
   email: the MJML output) inside a drawer, desktop/mobile widths.
3. Nothing else: catalogue, renderers and the newsletter domain live in the Riu project, not in
   Mateu (nothing Riu-specific in the framework).

Can ship before the control plane: it needs (1) + (2) in Mateu and the email catalogue + MJML
renderer on the Riu side.
