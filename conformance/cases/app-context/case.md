# app-context

Pins the application-level context selector: an @AppContext member of the app class must travel as AppDto.contextSelectors — fieldName "hotel", label "Hotel" (the explicit annotation label), and enum-derived options whose value is the constant name and whose label is the humanized name ("palma" → "Palma") — plus the derived "context-selectors" entry in requiredCapabilities. This is worth pinning because the selector is the contract every shell's header picker and the per-request appState merge depend on: the picked value is stored and re-sent under fieldName, and any screen reads it via httpRequest.appContext("hotel"), so a port drifting on fieldName casing or option value derivation silently breaks context reads across the whole app. The three servers derive the options from three different declaration sites (Java enum field, .NET enum property, Python method return annotation), which is exactly the kind of parallel derivation a shared corpus exists to keep aligned; the fixture uses lowercase enum constants in all three languages so the option values compare byte-for-byte.

## Known divergence

Both ports will likely xfail on strict equality for the same App-envelope reasons already documented for app-in-code: Java composes menu/home routes with the mount prefix (/conformance/app-context/a) and emits envelope members the ports' MenuItem/AppMetadataDto lack (path, type, totalMenuOptions, homeServerSideType carrying the Java inner-class name), and the Java core test environment's REST source catalogue leaks restSources plus a "rest-sources" requiredCapabilities token into the golden that the ports do not carry. The pinned semantics — one contextSelectors entry with fieldName "hotel", label "Hotel", options [palma→"Palma", madrid→"Madrid"] and the "context-selectors" capability token — should match member for member; anything beyond that differing is the shared app-envelope gap, not a selector gap.
