# validation

Pins how declared constraints reach the wire: @NotEmpty/@NotNull ([Required]/Required()) must surface as the FormField's `required` flag, and @Min/@Max must surface as component-level `validations` entries (ValidationDto: fieldId + client-side condition + message, built by ConstraintValidationMapper). This is what makes client-side validation backend-driven — a renderer refuses to submit based solely on what the wire says, so a server that drops a constraint silently ships a form that accepts invalid data. Worth pinning precisely because the three servers do NOT agree today: the ports set `required` but neither .NET's Wire.cs nor Python's mateu_dtos has a validations member at all, .NET's mapper never reads [Range], and Python has no min/max marker — a gap nobody had written down in one place.

## Known divergence

Both ports will xfail on the full-wire comparison. The `required` flag itself agrees everywhere (.NET ReflectionMapper.cs reads System.ComponentModel.DataAnnotations.RequiredAttribute; Python mapper.py reads the Required() marker), but the Java golden also carries ServerSideComponentDto.validations — four ValidationDto entries (NotEmpty name, NotNull email, Min/Max age, each with a state-expression condition and an English message) — and neither port's wire has a validations member at all (no ValidationDto in backend/dotnet/src/Mateu.Dtos/Wire.cs, none in backend/python/mateu_dtos). Additionally .NET's mapper never reads [Range] (it compiles and is declared here to record the intent), and Python cannot declare a numeric range at all. So the divergence is structural (a missing wire member), like the simple-form section divergence: a contract decision about whether validations are part of the spec, which the corpus makes visible.
