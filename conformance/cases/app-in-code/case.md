# app-in-code

Pins the code-authoring path for the app shell: an app whose chrome and whole menu are composed fluently via AppSupplier (Java) / IAppSupplier (.NET) / AppSupplier (Python), with no menu annotations at all. The wire must carry the app metadata — title, explicit variant, explicit home route, and a menu mixing the two shapes (a plain route leaf and a submenu nesting a child route leaf) — identically from all three servers. This keeps "the menu is data you can build at request time" a guaranteed cross-port capability rather than a Java-only idiom: it is the path a user-, config- or database-dependent menu takes, so a port silently dropping the supplier would only be discovered in production. Variant and homeRoute are pinned explicitly in the fixture because the three servers have different fallback rules (Java's AppShell defaults variant to TABS; the ports run the auto heuristic and derive home from the first menu item), and the corpus should compare the authored shell, not the fallbacks.

## Known divergence

Both ports will likely xfail on strict equality while the floor test (an app fragment with the menu) passes. Java's AppDto envelope is structurally richer than the ports' AppMetadataDto: it emits totalMenuOptions (a nonzero int, so it survives normalisation), and each MenuOptionDto carries members the ports' MenuItem does not have — notably `type` (MenuTypeDto) and `path` (Java's Menu/RouteLink records carry a path distinct from route). serverSideType also differs by construction (Java inner-class binary name vs Mateu.Tests.ConformanceAppInCode vs tests.test_wire_conformance.AppInCode), the same non-volatile type-name divergence every existing case already carries. Title, variant (MENU_ON_TOP), homeRoute (/a), menu labels/routes and the nested submenu should match exactly — those are the pinned semantics.
