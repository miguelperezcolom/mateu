# dashboard

**Pins:** the `Dashboard` archetype's composition on the wire — consecutive `MetricCard` fields grouped into one `Scoreboard` band (each card a `MetricCard` child carrying title/value/unit/trend/trendLabel, trend as a lowercase string), a `@Panel` component field wrapped in a titled `DashboardPanel` tile (title/subtitle/colSpan/rowSpan, content as a child), all inside a `DashboardLayout` grid. Chosen because it is the first archetype in the corpus: unlike a reflected form, the server COMPOSES this page from field conventions, so all three composers (Java `DashboardComposer`, .NET `ArchetypeComposers.ComposeDashboard`, Python `mapper.compose_dashboard`) must agree not just on member names but on grouping order and nesting. It also pins the tree-supplier envelope, where the ports are known to add a `Page` wrapper Java does not emit.

## Known divergence

Structural, both ports: Java's ComponentTreeSupplierMapper emits ServerSide → DashboardLayout directly — an archetype page gets NO Page wrapper/header in Java — while both .NET (ReflectionMapper builds a PageMetadataDto around the composed tree) and Python (mapper wraps ServerSide → Page → DashboardLayout, per test_ux_components.page_children) insert a Page component carrying the title between the ServerSide envelope and the DashboardLayout, and seed scalar properties into initialData for tree suppliers. Additionally the panel's Text content diverges member-wise: Java's TextDto carries container: "div" (a non-empty default the normaliser keeps), which the ports' Text metadata does not have. Expect both ports to xfail on the Page-wrapper altitude even though the DashboardLayout/Scoreboard/MetricCard/DashboardPanel subtree members agree.
