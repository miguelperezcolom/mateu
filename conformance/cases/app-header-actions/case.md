# app-header-actions

Pins the app-header actions contract on the wire: an app class implementing AppActionsSupplier (Java) / IAppActionsSupplier (.NET) / AppActionsSupplier (Python) must emit AppDto.contextActions with the exact AppHeaderAction shape — a plain button carrying actionId+label+icon, and a dropdown entry carrying a null actionId, a label, an icon and children that are the only dispatching leaves. It also pins the derived "header-actions" token in requiredCapabilities, which all three servers compute from the same declaration. This is worth pinning because header actions are per-request server-computed chrome (visibility follows server-side state), so a port silently dropping the supplier — or flattening the children — would render a shell with no way to reach those actions and would only be discovered in production; the child-vs-top-level distinction is behavioural (only children dispatch), so the nesting itself is the contract.

## Known divergence

Both ports will likely xfail on strict equality while the floor test passes, for the same reasons already documented on app-in-code: Java's AppDto envelope is richer than the ports' AppMetadataDto — it emits totalMenuOptions, and each menu option carries path/consumedRoute/uriPrefix/visible with the route composed under the mount ("/conformance/app-header-actions/..."), while the ports emit the raw route "/" (same for homeRoute/homeConsumedRoute). Additionally, the Java conformance harness's REST source catalogue leaks into every app golden: the Java expected.json will carry restSources (countries/orders/invoices) and a "rest-sources" token in requiredCapabilities that the ports do not have. The pinned semantics that must match exactly: the contextActions array — [{actionId:"sync", label:"Sync now", icon:"vaadin:refresh"}, {label:"Export", icon:"vaadin:download", children:[{actionId:"exportPdf", label:"As PDF"}, {actionId:"exportExcel", label:"As Excel"}]}] (the dropdown's own actionId null/omitted) — plus the "header-actions" capability token, the title "Header actions", the MENU_ON_TOP auto variant (one leaf, no submenus) and the "Home" menu label.
